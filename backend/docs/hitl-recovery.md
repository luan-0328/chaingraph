# 人工审批恢复与事件、消息幂等

## 为什么恢复会重跑代码

LangGraph 恢复 `interrupt()` 时会从暂停节点开头执行，并在相应 interrupt 调用处返回人工提交的数据。它不是恢复一个仍在内存中暂停的 Python 栈。因此 interrupt 前写事件也可能再次执行；节点完成前失败，动作节点也可能重跑。

## 本项目的去重方式

`agent_run_events` 和 `ticket_messages` 新增可空的 `dedup_key`，各自有唯一索引。旧记录保持 NULL，用户正常发言不带去重键，同样内容仍可发送多次。

| 逻辑操作 | 去重键示例 |
| --- | --- |
| 第一次等待人工 | `run:42:review:1:waiting` |
| 第一次人工决定 | `run:42:review:1:decision` |
| 第二次等待人工 | `run:42:review:2:waiting` |
| Agent 最终回复 | `run:42:ticket:100:reply` |
| 系统结单消息 | `run:42:ticket:100:resolved` |
| 退款副作用（已有机制） | `refund:run:42:order:200` |

审核轮次保存在 State 的 `human_review_round`：进入 human 时以旧值加一生成本轮键；真正取得人工结果、节点完成时才保存新轮次。因此同一次 interrupt 的首次进入与恢复，使用相同的键；后续真正再次转人工，则使用下一轮的键。

仓储直接尝试 INSERT，由数据库唯一索引裁决并发。冲突时只回滚 SAVEPOINT，再以共享锁当前读取回已有记录，避免旧快照以及排他锁升级死锁；其他约束错误仍然抛出。事件只有首次插入成功才广播到 SSE，重复请求不会再发一遍。

结单在同一事务内完成：锁定工单 → 检查本次结单键 → 更新状态 → 保存记忆摘要 → 写 Agent 回复 → 写系统结单消息。任一步失败整体回滚。若结单键已存在，不再改状态，也不会把用户后来重新打开的工单再次关闭。

## 审批恢复的完整流程

1. 用户触发处理，原子抢占 `tickets.agent_status`，创建 AgentRun 并生成 thread_id。
2. 带 thread_id 调用图。Checkpoint 保存图状态和待执行任务；AgentRun 保存执行元信息，两者不是同一份数据。
3. human 节点写入本轮等待审核事件，然后 `interrupt(payload)` 暂停。服务层把 run 和工单执行权记为 WAITING_HUMAN。
4. 客服请求批准或驳回。接口验证客服权限；服务查找当前等待的 run，取出原 thread_id。
5. 数据库原子抢占 `WAITING_HUMAN → RUNNING`，同时验证仍是同一个 agent_run_id。只有一个并发请求可以恢复。
6. 读取该 thread_id 的 Checkpoint，按实际进度处理：
   - **还有 interrupt**：`graph.ainvoke(Command(resume=决定), config)`。human 从开头重跑，等待事件由去重键挡住；interrupt 返回审批信息，节点保存审批结果及轮次。
   - **审批已保存，只剩 execute_action**：`graph.ainvoke(None, config)`。继续失败动作，沿用原审批人、决定和业务上下文；不允许把已保存的批准改成驳回，反之亦然。
   - **图已完成，只是 run 收尾未成功**：直接使用 Checkpoint 中的终态补记 AgentRun，不再执行图。
   - **不符合以上状态**：拒绝盲目恢复，要求人工核实。
7. 批准后动作走 Tool → Service。退款先检查幂等结果，命中成功记录就复用；否则 Service 在订单锁内检查规则，执行退款、库存变更。结果用 JSON 可序列化格式保存，包括把 datetime 转为字符串。
8. 原子结单、记录完成事件。更新 AgentRun 后，在 finally 中按原 agent_run_id 释放执行权；再次 interrupt 则保留等待人工状态。

驳回时先补齐转客服状态和交接消息，再结束 AgentRun。交接失败仍保留恢复入口；重试沿用 Checkpoint 中的原审批人和意见。

## 验证和边界

验证结果：全量 151 项通过（213.42 秒）；随后补齐驳回交接失败恢复，最终恢复、幂等和边界专项 43 项通过（81.18 秒）。Python 编译及 Git 空白检查通过。测试使用隔离 MySQL 库；恢复故障测试使用真实 LangGraph 与内存 Checkpointer、确定性模型桩，不代表物理进程退出后的恢复验证。

故障注入覆盖：退款成功后、结单后但动作 Checkpoint 保存前、图完成但 AgentRun 更新前发生异常。重试后退款成功流水只有一条、库存只回补一次、最终 Agent 回复和系统结单消息各一条。另有 Barrier 同时起跑的事件与消息插入测试，以及真正二次审批不被误去重的测试。

本次保证持久化事件和消息的逻辑幂等；SSE 仍是进程内实时通知。数据库提交后、广播前进程被杀，实时通知可能缺失，刷新工单详情可查看持久化事件。本次没有实现事务 Outbox、跨机器 Checkpoint 或后台自动接管。

已有结果快照缺失时仍转人工核实，不会把“认领成功”当成“退款成功”。异常重试与物理进程崩溃后的自动恢复不是同一个能力。

重启后端会通过现有 schema 同步补上新列和唯一索引；加列后清除结构缓存，确保同次启动能建索引。若曾在建索引前中断，下次启动会补齐。历史无去重键的数据不会自动合并。
